# Make activity

Start with the performance, then choose mechanics that reveal it. This design grammar is a practical synthesis, not a validated framework; a new activity is a proposed design, not a proven intervention.

## Design

1. **Use the brief.** Take the observable objective, knowledge kind, learner level, prior attempts and purpose (diagnosis, practice or assessment) from the calling skill or conversation. Fit time, resources, setting and accessibility needs. Ask only for missing information that materially changes the design; otherwise make reasonable assumptions.
2. **Lock the evidence.** Decide what the learner must do, what response shows it, and what counts as success. Preserve the objective and depth: a calculation task must still require calculation, even inside a decision or story.
3. **Choose a loop.** Select the simplest useful loop: prompt → learner action → evidence → feedback. Vary the thinking or information, not just the decoration. Don't generate alternatives unless the first design fails a check or the user asks.
4. **Make it usable.** Supply concrete prompts, data or materials, a checked answer or acceptance criteria, and feedback timing. Include setup, timing and facilitator guidance only when the setting needs them.
5. **Check it.** Is the task solvable, with sufficient information? Can the learner succeed without doing the target thinking? Execute code or check calculations when useful; verify uncertain facts. Mark unchecked keys unverified; recheck before rejecting a different answer. Allow multiple valid answers with explicit criteria. Remove irrelevant rules, speed pressure and reading load.

Match the action to the knowledge kind: **procedure** → do it on a new case; **principle** → predict or diagnose; **concept** → classify; **structure** → label parts or relationships; **facts** → recall. These are starting points, not mandatory formats.

## Return and pacing

- **Called by another skill:** return one activity with its evidence, key or criteria, and feedback plan internally. The caller controls scope, difficulty, hints, turn order, answer reveal, scoring and saving. Never turn one question into a menu, a multi-stage assignment or an extra clarification. In diagnosis, keep think-aloud separate from explanations requested afterwards; in tests, give no hints or keys before the answer. Adaptation and final transfer checks use this same design process. Once this skill is loaded, apply it directly; don't reread it or start a separate planning workflow for each activity.
- **Standalone:** present one ready-to-run activity by default. Separate learner instructions from the facilitator key. If delivering to the learner, show only the prompt and wait for their attempt before feedback. For group designs, include individual evidence where needed. Suggest a short pilot for a larger untested design.
- **With saved memory:** follow the learning folder's `AGENTS.md`. Return the design to the caller for saving; don't change progress on its behalf. Standalone, save only when asked, preserving learner-authored work.
