# Make activity

Start with the performance, then choose mechanics that reveal it. This design grammar is a practical synthesis, not a validated framework; a new activity is a proposed design, not a proven intervention.

## Design

1. **Use the brief.** Take the observable objective, knowledge kind, learner level, prior attempts and purpose (diagnosis, practice or assessment) from the calling skill or conversation. Fit time, resources, setting and accessibility needs. Ask only for missing information that materially changes the design; otherwise make reasonable assumptions.
2. **Lock the evidence.** Decide what the learner must do, what response shows it, and what counts as success. Preserve the objective and depth: a calculation task must still require calculation, even inside a decision or story.
3. **Choose a loop.** Consider a few alternatives internally and select the simplest useful one: prompt → learner action → evidence → feedback. Vary the thinking or information, not just the decoration. Use the choices below only when they help.
4. **Make it usable.** Supply concrete prompts, data or materials, a checked answer or acceptance criteria, and feedback timing. Include setup, timing and facilitator guidance only when the setting needs them.
5. **Check it.** Can the learner succeed by guessing, a shortcut or a teammate without doing the target thinking? Is information sufficient, the task solvable, and the evidence individual when needed? Check examples and keys: execute code when possible, solve calculations independently, and verify uncertain facts. Mark unchecked keys unverified; recheck before rejecting a different answer. Allow multiple valid answers with explicit criteria. Remove irrelevant rules, speed pressure and reading load.

## Choose the mechanics

| Choice | Possibilities |
|---|---|
| Action | Classify, predict, investigate, compare, construct, diagnose, repair, justify |
| Information | Complete, hidden, conflicting, progressively revealed |
| Interaction | Individual, paired critique, cooperative, distributed roles |
| Constraints | Meaningful limits on tests or resources, changed conditions, or none |
| Feedback | Test results, self-check, critique, facilitator prompt, delayed reveal |
| Evidence | Worked solution, classification, labeled parts, corrected error, tested artifact, explanation |

Reverse an outcome into inputs; diagnose a plausible error; reveal clues; compare alternatives; change a condition; or construct a counterexample. Combine patterns only when they strengthen the objective. Hidden information must be obtainable, and limited tests must still permit success.

Match the action to the knowledge kind: **procedure** → do it on a new case; **principle** → predict or diagnose; **concept** → classify; **structure** → label parts or relationships; **facts** → recall. These are starting points, not mandatory formats.

## Return and pacing

- **Called by another skill:** return one activity with its evidence, key or criteria, and feedback plan internally. The caller controls scope, difficulty, hints, turn order, answer reveal, scoring and saving. Never turn one question into a menu, a multi-stage assignment or an extra clarification. In diagnosis, keep think-aloud separate from explanations requested afterwards; in tests, give no hints or keys before the answer. Adaptation and final transfer checks use this same design process.
- **Standalone:** present one ready-to-run activity by default; show alternatives when asked. Separate learner instructions from the facilitator key. If delivering the activity to the learner, show only the prompt and wait for their attempt before feedback. For group designs, include individual evidence where needed. Suggest a short pilot for a larger untested design.
- **With a learning vault:** read its root `AGENTS.md` and follow its rules. Return the design to the calling skill for saving; do not create notes or change progress on its behalf. Standalone, save only when asked, using existing sections and preserving learner-authored work.
